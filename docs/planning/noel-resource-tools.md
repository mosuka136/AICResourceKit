### 1.3 仓库职责

| 仓库 | 负责内容 | 完成阶段 |
|---|---|---|

插件的通用替换能力也不应被 wardrobe 的生产规则缩减：保持既有 v2 Spine 分段替换、兼容映射、包优先级等功能；wardrobe 继续在自身规格与检查中约束“只改服装、动作不变、`effects.dirt=legacy`”。插件不读取 `progress.json`，不实现四目标顺序锁，不依赖 Python 或 wardrobe 的目录结构才能加载资源包。

### 2.2 开发约束

- 主插件目标框架是 .NET Framework 4.7.2，测试项目为 .NET 8；生产代码不能因测试可运行而引入主插件不支持的 API。主工程为 SDK 项目，新源文件由默认规则自动纳入；链接的共享源码仍需显式登记。
- 保持已有 v2 包和当前配置的行为；新资源类型复用总开关、资源包顺序、Sensitive 授权及错误隔离，不另建一套互不相干的配置。
- 插件按通用资源身份工作，Noel 名称只出现在调查资料和测试样例中，不硬编码角色白名单。
- 首先复用游戏已经解码的 PXL/MPCC 对象、图片和组合关系。插件接入不要求先在 Python 里完整重写这些格式。
- 开发测试使用原件往返或合成夹具，不生成服装，不改动 wardrobe 的设计确认和用户验收。
- 使用 Debug 构建；不构建主插件 Release，避免影响游戏可能使用的 Release DLL 符号链接。部署实测时单独说明 DLL、资源包和配置的写入位置及覆盖行为。
- 不重写游戏原始资源容器，不增加备份、快照或磁盘回滚流程。运行时关闭替换后恢复原对象属于现有生命周期行为，应继续正确实现。
- UTF-8、空格缩进、CRLF。测试与格式检查按插件仓库规则执行。游戏资源和反编译资料留在本机忽略目录，不提交完整原件。

## 3. 第一阶段工作包：AICResourceKit

### P01 · 调查实际加载路径并建立能力清单

**依赖：现有插件和只读资源目录。最先执行。**

- 结合 `ver030g` 的游戏程序集、调用方和资源目录，登记主立绘、MTI 单图、直接 `MTI.LoadImage`、Resources、PXL 内嵌/额外图片、普通 SpineViewer、PICT、MPCC 和视频的实际读取路径。
- 每项记录方法签名、调用参数、容器、JSON/图片键、缓存对象、消费者和释放时机。不能以文件名或 `Texture2D.name` 推断替换身份。
- 在插件内提供按目标筛选、默认关闭的诊断导出，记录发现目标、入口命中、候选应用结果和失败原因。不依赖 wardrobe 的 `resolve` 或新任务模型。
- 区分“代码路径已确认”“运行时已命中”“替换已生效”；没有触发不能记作成功，也不能记作资源不存在。
- 优先复核主立绘的通用 `key + jsonKey` 路径、PXL 外部主纹理，随后定位两个待确认 Sprite、atlas-only、额外 part/mask 页及视频调用方。

**输出：** 插件能力草表、真实加载键与来源对应表、待调查项。诊断报告是开发工具，不成为以后每套服装必须重复执行的固定验收。

**验收：** 已确认 141 组均有加载路径结论或具体待查原因；9 组待确认资源保留独立调查状态。一个目录项可以对应多个运行时目标，多个目录项也可以共同引用一个目标。

### P02 · 由插件定义目标身份和包格式

**依赖：P01。先形成可测试草案，P10 完成交接前定版。**

- 现有 v2 标识保持兼容：主立绘为 `key + jsonKey`；MTI 为 `assetKey + imageKey`；Resources 为 `path + objectType`。
- 新入口身份包含必要的加载器及容器范围，避免同名图片互相覆盖。内嵌图片需要稳定的原始图片标识；多页图集需要明确的页映射。字段以 P01 的真实读取参数为准。
- 区分来源对象 ID、运行时身份和样例包 ID。运行时匹配不依赖 Unity 临时实例 ID、绝对游戏安装路径、wardrobe 任务 ID 或导出文件名。
- 保留 `stand_battle.old` 的 `key=stand_battle`、`jsonKey=stand_battle.old`；PXL 主纹理的空 `imageKey` 按当前语义处理，不能错填成调用方的其他参数。
- 明确重复目标、目标重叠、多个包优先级、跨包共享文件、未知类型和失败目标的处理方式；已有规则不因增加入口而变化。
- 能沿用 v2 表达的目标继续使用 v2。新增语义若无法兼容旧格式，再增加版本，并让不支持该版本的插件明确拒绝；不先把所有包统一改成 v3。
- 将解析、身份生成和依赖枚举保持为可测试的公共逻辑。后续 wardrobe 复用该逻辑或其测试向量，不另写含义不同的解析器。

**输出：** 插件仓库中的目标格式说明、Schema/机器规则、正反例和兼容性测试。当前契约位于 [docs/resource-contract.md](../resource-contract.md)，Schema 与向量位于 `docs/resource-replacement/`；后续入口实现时同步完善这些文件。

**验收：** 旧包无需改写仍可加载；同名异容器、多 JSON、空图片键、重复目标、缺页和未知类型有明确结果。

### P03 · 补齐直接 MTI 图片与 Sprite 入口

**当前状态：** 已接入直接 `MTI.LoadImage`、缓存材质更新与 MTI 释放；单图容器避免重复应用。Resources 的未打包 Sprite 保留原网格和 UV，刷新与恢复原图保留替换引用，显式卸载时清理。自动测试通过；ver030g 已部署并用 `sakura-furisode-title-v1` 验证 `key_noel`、`difficulty` 的首次加载与标题、难度选择画面，两项诊断均为 `candidate-applied`。刷新、关闭和释放尚未完成实机验证。`wplmode_` 的实际加载参数，以及 `mgm_bun.pxls.bytes.texture_0`、`damage_backvoreenemy` 两个 Sprite 消费入口仍待确认，不标记为已验证替换。使用方式见[正式说明](../usage.md)。

**依赖：P01、P02。**

修改加载补丁、纹理注册与应用模块，优先复用现有纹理准备机制。

- 接入 `MTI.LoadImage` 的实际路径；`key_noel`、`difficulty` 的调用已确认，`wplmode_` 待真实入口证据后验收。使用容器与资源键匹配，不能全局拦截同名图片。
- 与已有 `LoadContainerOneImage` 补丁协调，同一对象只应用一次；处理首次返回、缓存持有、刷新和释放。
- 核对 `mgm_bun.pxls.bytes.texture_0`、`damage_backvoreenemy` 两个 Sprite 的来源。经过 Resources 时复用已有入口；确有其他创建路径再增加对应适配器。
- 审查现有 `CreateSprite` 的 `SpriteMeshType.FullRect` 实现，补齐适用目标的裁切、旋转、pivot、border、pixelsPerUnit、网格和 UV 语义。不支持的形态必须被检测并说明，不能显示错位后仍报成功。
- 处理调用方长期持有旧对象的情况：采用稳定引用更新或明确重绑消费者，而不是只修改下一次加载的返回值。

**验收：** 三张标题图及同名非目标图有匹配正反例；Sprite 的逻辑画布与实际裁切不混淆；刷新后已显示对象正确更新且无重复替换。

### P04 · PXL 外部、内嵌及额外页替换

**依赖：P01、P02、已有 MTI 机制。**

新增 PXL 图片适配器，必要时抽取共用图片注册逻辑。

- 复核外部主纹理 `LoadContainerOneImage` 路径，确认 `assetKey`、`imageKey` 与调用方加载参数的实际含义。
- 对内嵌图片，在游戏创建/解码并持有图片对象的位置接入；用 PXL 来源键与真实图片标识定位，保持原始帧和图层引用。
- 对 part、mask 及其他额外页逐页登记，不因主纹理可替换就宣称整套资源已支持。处理同一 PXL 同时包含外部和内嵌页的情况。
- 保留页面角色、尺寸、过滤方式、透明度、材质与遮罩关系。优先只替换图片，不改 PXLS 的帧序、方向、坐标、变换和时长。
- 共用图片的所有消费者都必须得到一致结果；刷新、关闭和释放不会遗留旧纹理或销毁游戏拥有的原始对象。
- 游戏已能读取的 `%IMGV_SECTION%` 等结构优先交由游戏处理。只有定位或应用所必需的字段才在插件侧补充读取；完整离线解析留给第二阶段。

**验收：** 外部 `noel.pxls`、内嵌 `noel_bassrobe.pxls`、`_icons_ttr.pxls`、`_icons.pxls`，以及混合页/额外页夹具均通过；一页失败不能静默变成整套成功。

### P05 · 普通 SpineViewer、剧情 Spine 与多页支持

**依赖：P01、P02。**

新增普通 SpineViewer 适配器；按需扩展 `SpineComposer`、纹理准备和 atlas 绑定。

- 覆盖 Fatal 使用的普通 `XX.SpineViewer`，按真实容器与 JSON 定位。不能把它伪装成 `SpineViewerNel` 或强行套上 `SvTexture`。
- 保留一包多个 JSON、历史变体及共享 atlas；同一个 JSON 切换不会污染其他骨架。
- 支持实际所需的多纹理页，建立页名、纹理、材质和附件的对应关系。解析、依赖枚举、准备、应用和释放同时具备多页能力后，才开放对应包格式。
- 保留游戏的播放状态、轨道、皮肤组合、事件、材质、遮罩和原效果。原图往返测试不能改变动作或剧情行为。
- 保持现有通用插件的分段替换和兼容能力。Noel 换装样例使用附件/图片修改并保留原动作及污渍；wardrobe 的更严格生产检查在第二阶段接入。
- 复核 37 个主立绘的现有通用路径；新增 33 个主立绘无需硬编码成 33 条补丁。主立绘与普通 SpineViewer 的身份及缓存边界明确分开。

**验收：** 主立绘历史 JSON、单骨架剧情、同屏多骨架、`fatal_nusi_1` 共享依赖和多页夹具均能独立加载；原有主立绘效果与预览行为不回归。

### P06 · 独立 atlas 与剧情 PICT / EF_PICT 图片

**依赖：P01、P02、P03/P05 的相关图片和 atlas 支持。**

- 找到剧情直接持有 atlas 区域或纹理的绘制路径。图片即使没有被骨架 attachment 引用，也必须能替换。
- 区域级目标与整页目标采用明确语义：可以以整页图片替换承载区域编辑，但运行时身份和共享影响必须准确，不能伪造骨架 JSON。
- 覆盖 `cuts_nightingale_0_0` 的 `noel_peeping__0000/0001/0002`；这些图片在默认骨架姿态之外由剧情指令使用。
- `damage_backvoreenemy.atlas` 按实际 atlas/纹理消费者接入，不把“有 atlas”当作“有可替换骨架”。
- 同一 atlas 同时被 Spine 和 PICT 使用时统一处理共享对象；保留区域旋转、透明边距、位置、材质及遮挡关系。

**验收：** 默认骨架外的 Noel 图片能独立命中，atlas-only 样例无需 JSON；共享页刷新后骨架和剧情图片一致，其他区域保持原样。

### P07 · MPCC 运行时资源调查与接入

**依赖：P01、P02、P04/P06 的可复用入口。**

- 查明五个 `mobpcc/*.mpcc.bytes` 文件的实际读取类、组合对象、图片/部件来源和缓存关系。
- 逐项调查 `noel__231022_013830`、`NOEL__231022_013830_2`、`NOEL__darknoel`、`sub_i__231022_162602`、`sub_i__mzh`，记录角色归属及加载证据。
- 优先从游戏已经解析出的组合对象取得依赖和可替换图片，不要求 wardrobe 先写 MPCC 解析器。
- 若只是引用已有 PXL/纹理，复用对应适配器并输出映射；确有独立图片或二进制组合需求才增加独立类型。
- 若必须支持数据文件替换，明确字段、版本与兼容限制，不能提供盲目替换未知二进制的入口并宣称已完成角色覆盖。

**验收：** 五项都有依赖和入口调查结论；已确认目标可通过插件独立样例包验证。仅保留原二进制、仅靠名字含 Noel 均不算完成调查。

### P08 · 视频加载替换

**依赖：P01、P02。**

- 查明视频实际使用的 VideoClip/播放器/加载容器及缓存方式，再确定稳定资源身份。不能先假定只有 `VideoPlayer.url` 一种使用方式。
- 接入已确认的 `tuto_energyball`、`tuto_watershard`、`tuto_watershard07`。保留其他两个视频的调查结果，避免按近似文件名误替换。
- 支持外部候选媒体的准备和加载，保持原分辨率约束、播放时间轴、循环、音轨、结束事件及游戏调用语义。
- 不重写原 AssetBundle。无法满足播放器要求的编码、尺寸或播放属性，返回明确错误。
- 明确播放中的刷新时机、切换失败和资源释放策略；关闭或失去授权时沿用原有替换系统的有效性规则。
- 加密视频如需可播放的临时解密文件，必须有明确生命周期、清理与授权撤销处理；无法支持的组合明确拒绝，不绕过资源 IO。

**验收：** 三个目标分别完成正确匹配、实际播放、循环/结束和释放验证；不以“文件能导出”或“FFmpeg 能解码”代替游戏加载成功。

### P09 · 统一刷新、授权、诊断与配置体验

**依赖：P03–P08，随各入口逐项接入。**

- 新类型复用现有包排序、启用/关闭、Sensitive 授权、刷新和错误隔离；同一身份在所有模块中采用同一比较规则。
- 复用准备任务及应用调度，取消或淘汰过期结果，防止异步旧结果覆盖当前选择；Unity 对象操作保持在适当线程执行。
- 明确原对象、替换对象和共享对象的所有权，处理多消费者、读档、场景切换、卸载和重复刷新。
- 保留当前主立绘临时预览规则。普通图片、剧情和视频不强行触发主立绘姿态切换；需要状态显示时提供对应资源的加载结果。
- 配置与错误信息能区分目标不支持、未加载、已应用和应用失败。未知包版本、缺失依赖和错误字段指出具体包/目标/文件。
- 更新中英文说明，使新能力与真实行为一致。诊断导出必须能够供第二阶段读取，但不把开发日志放进正常用户换装流程。

**验收：** 旧包与新类型同时启用时顺序稳定；共享资源无重复销毁；过期任务不覆盖新结果；撤销授权及错误包处理保持既有规则。

### P10 · 加密工具、兼容测试与插件接口交付

**依赖：P01–P09。回归测试从开发开始持续维护，最终在此收束。**

- 扩展 `AICResourceKit.ResourceEncryptor` 的依赖枚举。当前工具主要枚举 v2 的 `image`、`atlas`、`spine.json`；新增页、内嵌图替换文件、视频等必须按已定版格式完整枚举。
- 包解析、加密、资源准备与加载共用依赖规则；共享文件去重、相对路径和 Sensitive 规则保持一致。未引用的工程文件不误打包，引用的新资源不漏掉。
- 为格式解析、目标身份、共享依赖、匹配、取消/刷新、权限变化和错误路径增加 xUnit 测试，复用现有测试夹具。
- 提供不依赖 wardrobe 的最小测试包及复现步骤。单元测试使用小型合成资源；真实游戏原件及本地实测结果不纳入 Git。
- 定版接口文档、Schema、能力清单和样例，更新现有替换说明。区分编译版本声明的能力与本次实际完成的运行时验证。

**第一阶段交付物：**

| 交付物 | 要求 |
|---|---|
| 插件实现 | 上述通用入口、资源应用与生命周期，不依赖 wardrobe |
| 包格式契约 | 字段、身份、页/文件依赖、优先级、错误、旧 v2 兼容规则 |
| 能力清单 | 插件版本、游戏基线、支持类型、限制和验证状态；机器可读 |
| 加载键报告 | 来源对象对应实际 runtime identity、调用证据与共享消费者 |

| 验证报告 | 自动测试与实际入口命中/应用结果分别记录；未完成项明确列出 |

**阶段切换条件：** 插件接口已经定版，计划范围的加载能力已实现并完成对应验证，旧资源包回归通过，样例包可由插件独立使用。未验证或未实现的项继续留在第一阶段，不用提前修改 wardrobe 来掩盖入口缺口。

## 4. 两仓库之间的接口交接

接口由 `AICResourceKit` 维护，wardrobe 消费。后续遇到新需求，先在插件确认真实入口及格式能力，再扩展制作器。

| 交接内容 | 插件必须说明 | wardrobe 后续用途 |
|---|---|---|
| runtime identity | loader、范围、精确键、空值及大小写语义 | 从目录对象解析实际目标 |
| 资源文件 | 格式、尺寸、透明度、页名、图片标识、媒体属性与路径规则 | 构建正确的候选和包 |
| 原始布局 | 是否允许换页、重排、扩容及相应限制 | 限制规格和编辑范围 |
| 依赖规则 | 多 JSON、共享页、PICT、PXL 图片及跨目标关系 | 去重、列出共同影响、完整打包 |
| 应用语义 | 首次加载、刷新、播放中切换、释放、错误处理 | 生成准确的安装与测试说明 |
| 能力与版本 | 哪一插件版本支持哪些类型，哪些经过实测 | 构建/安装前给出明确兼容结果 |
| 解析和测试向量 | 合法/非法 manifest、身份及文件枚举预期结果 | 复用共享解析或验证一致性 |

插件的机器报告不应依赖当前绝对目录。可以引用来源容器、对象标识和运行时参数，wardrobe 再结合本机游戏路径定位。报告中的“未命中”与“已排除”不得混用。

## 6. 实施顺序

```text
第一阶段：AICResourceKit
    P01 加载调查
        ↓
    P02 插件身份与格式草案
        ↓
    P03 图片/Sprite → P04 PXL → P05 Spine → P06 PICT/atlas
        ↓

        ↓

    W01 读取契约并解析目标 → W02 接入任务与适配器
```

P09 的生命周期与 P10 的测试随每个插件入口实施，不等所有功能写完才补。这个顺序表示先完成插件交付，再开始 wardrobe 代码修改；插件入口的调试样例不能成为提前开发 wardrobe 的理由。

第二阶段内优先接入新增主立绘和已验证的固定布局图片，再接入复杂像素、剧情和视频制作。实际服装仍遵守现有逐目标制作及用户验收规则，工具开发完成不代表服装已完成。

### 7.4 完成定义

- 第一阶段完成：插件独立具备已交付范围的替换能力，格式与依赖规则定版，旧功能回归通过，入口实测和供下游使用的契约齐全。缺失或未验证的能力仍列为第一阶段待办。
- 第二阶段完成：wardrobe 按已交付接口完成资源选择、生成图制作、检查、预览和交付，现有流程与用户记录保持兼容。
- 全视觉覆盖完成：来源、角色归属、独立图片、共享图集、动画和视频逐项闭合；未解决清单不能靠删除警告或仅保留二进制归零。
- 服装验收仍由用户反馈决定，只在任务 `progress.json` 保存用户原话；开发测试、入口验证和 Agent 审图都不能写为用户确认。
